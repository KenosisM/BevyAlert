# 地形接缝 —— 三份成品实现的调查

起因：`ra2engine` 的地面/悬崖交界处出现细黑缝（把兜底黑改成洋红后确认就是"没被任何砖写到的像素"）。
用户指令：**别实测、别猜**，去读三份能跑的成品（C++ 版、地图编辑器、地图渲染器），照它们的实现办。

本文只写**从代码里读到的事实**，附文件位置。推断单独标出。

---

## 0. 结论（先给要点）

**三份成品没有一份是把砖当"几何"画的。** 它们全都是：**把砖当屏幕空间的整数像素位图，逐像素决定"这个像素归谁"，索引 0 的像素直接跳过。**
深度用**逐像素 z 缓冲**（原版 / C++ / ccmaps）或**按高度的 stencil**（FA2 的 DX 路径）。

所以"缝"这个概念在它们那里**不存在**：决定一个像素归属的判据只有一个（整数值 + 索引 0 + z），
而我们的 Rust 端把这件事拆成了**三个互不保证一致的判据**：

1. GPU 三角形的像素中心覆盖（浮点、含 MSAA 采样覆盖）
2. 纹理 alpha ≥ 0.5（按 **texel** 量化——与像素网格不是同一张网格）
3. 深度测试（平局还要靠我们额外加的 `DEPTH_EPS` 去掰）

三者只要有一处不一致，屏幕上就是"没有砖占用"的像素 —— 即缝。

## 1. 成品一：RA2REASM 的 C++ 渲染器

工程：`I:\bevy\RA2REASM\src\`

### 1.1 绘制接口本来就是"屏幕空间精灵"

`src/render/renderer.h:27-41`
```cpp
struct DrawItem {
    const uint8_t* pixels;   // w*h 索引字节
    const uint8_t* palette;  // 768 字节 RGB
    const int16_t* zbuf;     // 逐像素 z（w*h），没有就用 zConst
    int w, h;
    int ox, oy;              // 世界坐标 = **屏幕像素**
    int16_t zConst;
    bool depthTest;   // false -> 无条件写
    bool tieWins;     // 平局保留**后画的**
    bool writeDepth;
};
```
注释原文（`renderer.h:24-26`）：*"One draw call for an indexed sprite (a TMP cell, an SHP frame, an overlay piece). The frame stores 8-bit palette indices."*

→ **`ox/oy` 是整数屏幕像素，不是世界坐标。**

### 1.2 CPU 参考实现：逐像素、整数、索引 0 跳过、z 平局规则

`src/render/cpurenderer.cpp:29-78`
```cpp
const float sx = (it.ox - cam_.x) * cam_.scale;
const float sy = (it.oy - cam_.y) * cam_.scale;
const int bx = (int)std::floor(sx), by = (int)std::floor(sy);
...
const float fx = (px - sx) / cam_.scale;
const int ix = (int)std::floor(fx);
const uint8_t idx = it.pixels[row + ix];
if (!idx) continue;                    // ← 索引 0 = 透明，**没有任何 alpha 混合**
const int16_t z = it.zbuf ? it.zbuf[...] : it.zConst;

    if (it.tieWins ? (z < zBuf_[o]) : (z <= zBuf_[o])) continue;

```
注释原文（`cpurenderer.cpp:56-57`）：*"tieWins keeps the later (equal) draw; strict form keeps the earlier one. Mirrors the game's two blit variants."*

→ **一个屏幕像素只由一个 fragment 决定；要么写满，要么不写。没有半透明、没有抗锯齿、没有覆盖不足。**

### 1.3 GPU 后端：**计算着色器逐像素合成**，不是三角形

`src/render/gpurenderer.cpp:1-7` 注释原文：
> *"the logic/asset code still emits plain DrawItems, but here they are **rasterized by a D3D11 compute shader** instead of the CPU loop. The shader reproduces the engine's exact raster math — palette expansion, the two depth-test tie rules, the shadow half-darken — so it can be validated pixel-for-pixel against the CPU reference. **Depth is resolved with atomic operations on a shared z-buffer UAV**, which is the faithful GPU equivalent of the CPU's per-pixel z test."*

`gpurenderer.cpp:149-202` `kSpriteHLSL`（**这就是 C++ 成品在 GPU 上画地形/单位的那段 shader**）：
```hlsl
[numthreads(8,8,1)]
void cs(uint3 dtid : SV_DispatchThreadID) {
    float sx = (ox - camX) * camScale;
    int baseX = (int)floor(sx), baseY = (int)floor(sy);
    int px = baseX + dtid.x, py = baseY + dtid.y;      // 一个线程 = 一个屏幕像素
    int ix = (int)floor((px - sx) / camScale);         // 整数最近邻取样
    uint idx = srcTex.Load(int3(ix, iy, 0)).r;
    if (idx == 0) return;                              // 索引 0 跳过
    int z = hasZbuf ? zsrcTex.Load(int3(ix, iy, 0)).r : zConst;
    if (depthTest) {
        InterlockedAdd(zbuf[cp], 0, old);
        bool win = (mode == 1) ? (z > old) : (tieWins ? (z >= old) : (z > old));
        if (!win) return;
        if (writeDepth) { ... InterlockedCompareExchange(zbuf[cp], cur, z, orig); ... }
    }
    float4 p = palTex.Load(int3((int)idx, 0, 0));
    color[cp] = float4(p.rgb, 1.0f);                   // 不透明写入
}
```
`gpurenderer.cpp:954-1004` `drawSprite` 只是把这个 CS 按 `(bw+bh)` 的**像素包围盒** dispatch 出去。

→ **GPU 上也是：屏幕空间 color+z 两个 UAV，逐像素写，用原子操作做 z 缓冲；没有顶点、没有三角形、没有采样器、没有 alpha。**

### 1.4 地形这块砖怎么摆（`src/tools/wwread.cpp`）

- cell 的屏幕位置（`wwread.cpp:1373-1374`）：`ox = dx * 30`、`oy = (dy - z) * 15` ← **纯整数**
- 主图与 extra 的绘制（`wwread.cpp:2406-2434`，实时客户端同样代码在 `4127-4152`）：
  ```cpp
  di.ox = c.ox; di.oy = c.oy; di.tieWins = true;      // 主菱形
  ...
  de.ox = c.ox + c.exX; de.oy = c.oy + c.exY;          // extra（崖壁/坡面）
  de.depthTest = c.extraDepthTest; de.tieWins = true;
  ```
- **实时客户端把地形烘成 480×240 的 chunk 图**（`wwread.cpp:4090-4168`），注释原文：
  > *"The terrain is static, so it is rendered once — but as a GRID OF CHUNKS, not one big image. The client blits only the chunks the view touches... **A tile sprite that spills past a chunk boundary is drawn into every chunk it reaches and each renderer clips it, so the seam between chunks is exact.**"*

  原文还特别写了漏 extra 的后果（`:4113-4119`）：*"a cliff wall is stored up to 60 pixels ABOVE it. Testing the diamond alone therefore drops a tile whose diamond sits past the chunk edge while its face still lands inside the chunk, and **the face vanishes from that chunk**: the tile underneath shows through as a hard-edged patch cut off exactly along the chunk border."*

- 砖的 z：`tileZBase = (rx + ry) * pitchY`，逐像素 `zbuf[i] = tileZBase - zData[i]`（`wwread.cpp:1384-1394`）—— **深度来自 TMP 自带的 z 数据**，不是几何。

## 2. 成品二：ccmaps-net（地图渲染器）

工程：`I:\bevy\RA2REASM\ref\ccmaps-net\`，核心 `CNCMaps.Engine/Rendering/TmpRenderer.cs`

画布是一整张 `W*60 × H*30` 的图（`Map.cs`），逐像素写。主菱形**连矩形图都不生成**，直接按行算跨：

逐像素判定（`TmpRenderer.cs:90`）：
```csharp
if (paletteValue != 0 && 在画布内 && (!useZ || zBufVal >= zBuffer[zIdx])) { 写 BGR; zBuffer[zIdx] = zBufVal; }
```

- `paletteValue != 0` —— **索引 0 不画**（不是 alpha）

## 4. 菱形台阶的精确形状（三份一致，可直接当规格）

`decode_diamond`（我们的 `src/tmp.rs:14-43`，逐行照抄 C++ `compat/tmp.cpp:18-39`）
与 ccmaps `TmpRenderer` 的 `cx += 4 / x -= 2`、FA2 的 `TilePixels` 三者吻合：

设砖矩形左上角为 `(ox, oy)`，`w = 60, h = 30`，则第 `r` 行（`r = 0..29`）的不透明像素区间为：

| r | 区间（相对 ox） | 宽度 |
|---|---|---|
| `0 ≤ r ≤ 14` | `[28 − 2r, 32 + 2r)` | `4 + 4r` |
| `15 ≤ r ≤ 28` | `[2r − 28, 88 − 2r)` | `116 − 4r` |
| `29` | 空 | 0 |

总像素数 = 480 + 420 = **900** = `60*30/2`（与 TMP 的 `diamondBytes` 一致）。

**相邻两格在屏幕上逐行互补（这是"无缝"的真正来源）**：

- 右邻格 `B = A + (30, 15)px`：屏幕行 `Y` 上，A 取第 `Y−oy_A` 行、B 取第 `Y−oy_B = Y−oy_A−15` 行。
  A 的区间右端 = `88 − 2r`；B 的区间左端（展开成 A 的坐标系） = `30 + (28 − 2(r−15)) = 88 − 2r`。
  → **首尾相接，不重叠也不留空。**
- 左邻格 `C = A + (30, −15)` 同理互补。

→ **只要位置落在整数像素上，菱形区域精确铺满平面，缝在数学上不可能出现。**

## 5. 我们的实现（现状）

`src/terrain.rs:321-393` `build_mesh`：

- 每块砖 = 一个 **`w×h`（60×30）的四边形**，UV 覆盖**整张砖位图**（含透明角）
- 位置 = 格角屏幕位置 − 30px，高度按 level 抬；四边形在 `y = level·LEVEL_HEIGHT` 的水平面内
- `src/game.rs:722-724`：`ImageSamplerDescriptor::nearest()` + `lod_max_clamp = 0`
- `src/game.rs:757`：`alpha_mode: AlphaMode::Mask(0.5)`
- `src/game.rs:733-743`：法线全部写 `(0,1,0)`
- 深度：GPU 深度缓冲 + 我们自加的 `DEPTH_EPS = 1e-3`（`terrain.rs:319`，沿相机光轴偏置，按 `(rx+ry)%8` 排序）
- **没有任何地方设 `Msaa`** → 用 bevy 默认值 `Msaa::Sample4`（已核：`crates/bevy_render/src/view/mod.rs:248-258`，`#[default] Sample4`）

## 6. 差异（结构性，不是参数问题）

| 项 | 三份成品 | ra2engine 现状 |
|---|---|---|
| 几何 | **没有几何**，屏幕空间像素 | 世界空间四边形 + 透视/正交投影 |
| 取像素 | `floor((px-ox)/scale)` 整数最近邻 | GPU 纹理采样（nearest + 无 mip） |
| 透明度 | 索引 0 **不写**（无 alpha、无混合） | `AlphaMode::Mask(0.5)`（按 texel 判 alpha） |
| 深度 | 逐像素 z 缓冲（平局后来者赢） | GPU 深度缓冲 + 手工 `DEPTH_EPS` 偏置 |
| 抗锯齿 | 无 | **MSAA 4x**（默认） |
| 像素归属判据个数 | **1 个** | **3 个**（覆盖 ∧ alpha ∧ 深度） |

**待验证（不得当成结论）**：缝的确切触发条件是哪一个判据失配 —— MSAA 的部分覆盖采样、
texel 量化边界与像素边界错位、还是深度平局。三者的共同点是：**它们都只在"把砖当几何"的
方案里才存在**；照抄成品（改回屏幕空间逐像素）之后，这个问题整体消失，不需要单独归因。

## 7. 设计决策（待用户拍板）

**地形渲染路线**：

- **A. 照 C++ 成品的实时客户端**：把地形**烘成 chunk 图**（逐像素 z 缓冲 + 画家序 + 索引 0 跳过），
  再按整数位置贴出来。地形从此没有几何、没有 alpha、没有 MSAA、没有深度平局 —— 缝在机制上不可能出现。
  与 C++ 版可直接逐像素对拍。代价：地形改动（建筑/爆炸/矿石）要重烘对应 chunk。
- **B. 照 C++ 成品的 GPU 后端**：在 Bevy 里加**计算着色器**逐像素合成（屏幕空间 color + z UAV，
  原子 z 缓冲，索引 0 跳过）。与 A 等价但全程 GPU，代价是 Bevy 侧要写自定义 render node。
- **C. 保留 3D 四边形**，但把菱形改成**参考实现的台阶多边形**（几何自带形状、不吃 alpha）+ **关 MSAA**。
  改动最小、仍在 3D 管线里；但属于"等价改写"，不是逐行照抄，且 extra 矩形仍要靠 alpha。
- **D. 保持现状**，只关 MSAA / 调参数。治不了根。
