## 1. compute_battle_sim

- 仓库：<https://github.com/Biped-Potato/compute_battle_sim>
- 语言/栈：Rust、bevy 0.15、WGSL compute（Custom RenderGraph Node）【读到】
- 规模：31★，3 fork，2024-12-25 建仓，最后 push 2026-03-22【读到 GitHub API】
- 配套讲解：<https://www.youtube.com/watch?v=TskJt4tlGfU>（我没看视频，只读代码与 README）

### 它到底做了什么（一句话）

在 bevy 里用 WGSL compute shader 全 GPU 跑「红蓝两军互推 + 索敌 + 扣血」的 2D 战斗模拟，靠空间哈希 + 双调排序把邻居查询压到 9 宫格，声称百万单位实时、峰值 200 万。

### 关键技术点（全部【读到】源码）

**数据结构（`assets/shaders/logic.wgsl`）**

```wgsl
struct Unit {                     // 32 B/单位，AoS，单个 storage buffer
  previous_state: vec2<f32>,      // 上一 tick 位置（给渲染插值用）
  current_state : vec2<f32>,
  velocity      : vec2<f32>,
  hash_id: i32, attack_id: i32, id: i32, health: i32,
}
```

- 三个绑定：`units`(storage) / `indices`(storage，每格起始下标) / `uniform`(参数)。
- uniform 里带 `level`、`step` 给双调排序用，带 `alpha` 给渲染插值用。

**参数（shader 顶部 const，直接可抄的量级）**

| 常量 | 值 | 含义 |
|---|---|---|
| `workgroup_s` | 256 | workgroup 大小 |
| `GRID_SIZE` | 5（main.rs） | 空间哈希格边长（世界单位） |
| `WORLD_SIZE` | 3840 × 2160 | 哈希网格 768 × 432 = **331,776 格** |
| `COUNT` | 524288（= 2^19，由 500000 向上取 2 的幂） | 单位数 |
| `protected_range` | 4.0 | 互斥半径（≈0.8 格） |
| `avoid_factor` | 2.0 | 互斥力系数 |
| `targeting_factor` | 0.5 | 朝敌/朝 midline 的吸引系数 |
| `max_speed` | 0.5 | 每 tick 位移上限 |
| `war_zone` | 5.0 | 中线争夺带半宽 |
| `attack_range` | 20.0 | 索敌半径（=4 格） |
| `kill_range` | 4.0 | 扣血距离 |

**每 tick 的 4 个 dispatch（`src/logic.rs` 组织）**

1. `hash`：`hash_id = x + y*grid_width`，`x = pos.x/grid_size + grid_width/2`（无 clamp）。
2. `sort`：**双调排序（bitonic）**，外层 `level = 2^1..2^n`，内层 `step = 2^k..1`，每次 dispatch `COUNT/(2*256)` 个 workgroup，机内原地比较交换 `units[a]/units[b]`。
3. `hash_indices`：因为已按 `hash_id` 排序，只需判断「我的 hash_id ≠ 前一个」就把 `indices[hash_id] = 我`；没被写到的格保持初值 **-1**。
4. `update`：遍历 9 宫格 → 从 `indices[cell]` 起顺序扫到 `hash_id` 变化为止。

**互斥力公式（第 1 个可以直接抄的公式）**

```wgsl
if (dist < protected_range) {
  let norm = normalize(offset);
  velocity += norm * avoid_factor * (protected_range / dist);   // 1/d 反比
}
```

**限速方式（第 2 个可抄的点，但写法很怪）**

```wgsl
velocity = normalize(velocity) * clamp(length(velocity), -max_speed, max_speed);
current_state += velocity;
```

即：**先归一化方向，再把「速度长度」夹到 [-0.5, 0.5]**，等价于恒速 0.5 前进（长度永远被夹到 0.5，因为长度非负）；`-max_speed` 下界是无效代码。【读到 + 推断】

**渲染插值（第 3 个可抄的点）**

`logic.rs` 里用 `FixedTimestep` + accumulator：`alpha = accumulator / timestep`，渲染时按 `previous_state → current_state` 插值，sim 用固定步长、渲染用刷新率。这是「连续运动」看起来不抖的关键。

### 有没有量化数字

- 有，但**是作者自述、无硬件型号**：README 原文 "simulate upwards of 2 million units in realtime"，"can at times be run at a stable 60 fps with 1 million units on my machine"【读到】。
- README 同时承认缺陷：超过 100 万跑久了会崩；"the project in its current form seems to regress in framerate the more it runs"【读到】。
- 仓库里有 `img/1million.png` 截图。【读到文件存在，未看图】

### 对我们的可借鉴点

**能直接落地：**

1. **`previous_state / current_state` 双位置 + alpha 插值**。我们现在「连续运动」如果直接在渲染帧推进位置，低 sim 频率下必然见抖；照抄这个结构（`PrevPos`+`CurPos` 两个 component 或 SoA 数组）。
2. **空间哈希 → 排序 → 每格起始下标 → 9 宫格扫** 这套「排序后同格连续」的思路，**但不要抄它的排序算法**（见下）。CPU 侧对应的是 `Vec<(cell_idx, unit_idx)>` + `sort_unstable_by_key` 或直接计数排序。
3. **`1/d` 反比互斥**在「已经重叠」时会爆炸（d→0 时力→∞），它的 `dist > 0.1` 之类保护**没写**（compute_battle_sim 里完全没有下界保护）。所以公式方向可抄、**必须自己加 `max(d, eps)` 或改成 `f²/d`**（见 §5 的写法，那个已经有 `f = 1 - d/r` 的软截断）。

**不适合，以及为什么：**

- **双调排序管线**：n = 524288 时 log2(n) = 19，总 pass 数 = Σk = **190 次 dispatch**；而 `logic.rs` 每次 pass 都 `create_buffer_with_data` 新建一个 uniform buffer（190 次/帧的 CPU 侧分配）。【读到代码结构 + 推断为帧率随时间退化的重要原因之一】我们在 CPU 上做全局比较排序本来就不需要，用**计数排序 / 每格两条 atomic 计数器做 bucket** 更合适。
- **`indices` 初值 -1 + 无 clamp 的 `hash_id`**：空格子会让 `for i in start_index..unit_count` 从 -1 开始扫，等于退化成 O(n) 全表扫；越界格也没有边界保护。【读到；O(n) 退化的后果是推断】。我们若用「每格 bucket」，空格子天然是空 list，没有这个问题。
- **无原子操作扣血**：B 站同作者（不同项目）也承认「伤害并行但没用原子操作，所以会丢伤害」【读到评论】。RTS 伤害必须确定性/可重放，这条绝对不能学。

## 2. bevy_crowd_sim

- 仓库：<https://github.com/Biped-Potato/bevy_crowd_sim>
- 语言/栈：Rust、bevy 0.16、WGSL compute【读到】
- 规模：13★，0 fork，2025-08-31 建仓，最后 push 2025-11-22【读到】
- 配套讲解：<https://youtu.be/A35sY2CthTU>

### 它到底做了什么（一句话）

同作者的「城市人流」版：市民沿**人工铺的路面砖**走路、到路口随机转向、互相挤开，全 GPU 更新，用来演示百万级市民。

### 关键技术点（全部【读到】`logic.wgsl`）

**数据结构（拆成两个 buffer，比 §1 更干净）**

```wgsl
struct Citizen     { current_state, previous_state: vec2<f32>, frame: u32, type_index: u32 }
struct CitizenData { velocity: vec2<f32>, hash_id: i32, old_grid: i32, intersection_decision: i32 }
struct Road        { frame: u32 }         // 每格路砖的「图形编号」
```

**方向从哪来（关键差异：不是流场）**

- 路砖 `frame` 取值：`1` / `2` = 直路（分别按 `local_x` / `local_y` 判断该往哪边走），`3` = 路口，其它 = 空地。
- 在直路上：用 **格内局部坐标** 反推车道偏移，硬编码 `24.0`、`7.+8.`、`48.-7.-8.` 这些像素阈值（说明路砖是 48×48）→ 得到「靠右行驶」的方向。
- 在路口：`intersection_decision` 缓存「直行 / 转弯」的分支；靠 `old_grid` 记住来向，再检查目标格是不是路，不是就改决策。
- **在空地上**：向 ±x / ±y 各扫最多 20 格找最近的路砖，找到就朝那边走。

**随机决策（可抄的小技巧）**

```wgsl
if (fract(sin(5.1300419567 * f32(index) - time * 1.681049) * 59.13910398) < 0.5)
```

纯 hash 伪随机，无状态、无 RNG buffer、每帧稳定。**【读到】** 这就是「打破对称」最便宜的做法。

**分离力参数**

`avoid_factor = 6.0`、`protected_range = 12.0`（=1.5 格）、`max_speed = 2.0`；公式与 §1 完全相同（`norm * avoid * (range/dist)`），同样 9 宫格、同样「从 `indices[cell]` 扫到 hash 变化为止」。

**动画**：`frame` 用 0–3（上）/ 8–11（下）/ 4–5（右）/ 6–7（左），`animation_timer` 每 0.1 s 推进一格。

### 有没有量化数字

- 只有 README 一句 "capable of simulating millions in realtime"【读到】，**无单位数、无帧率、无硬件**。

### 对我们的可借鉴点

**能直接落地：**

1. **`fract(sin(...))` 式确定性 hash 随机**：用于「路权抢行时谁先走」「同格多单位推开方向」「阵型微扰」，避免每单位维护 RNG 状态，也避免每帧结果跳变（用 `time` 或 `tick` 做种子可控制变化频率）。
2. **`Citizen` / `CitizenData` 冷热分离**：渲染要的（位置、帧）和逻辑要的（速度、哈希、决策）放两个 buffer。bevy 里对应「渲染组件」与「模拟 SoA」分离，减少每帧要同步的字段。
3. **「车道偏移」这个思路本身**：不是寻路，是**把「怎么走在格子里」编码成局部坐标规则**。RTS 里等价物是「单位在格内的站位（slot）」，比纯互斥力更能防抖。

**不适合，以及为什么：**

- **空地靠 ±20 格线性扫描找路 —— 这不是流场，是局部吸附**。遇到大片空地 / U 形墙 / 需要绕远的目标必失效。【推断，基于代码逻辑】我们已经有共享流场，长程绝不要退化到这种搜索。
- **路口决策用 50/50 纯随机**：RTS 里会让同一批坦克在同一个路口反复抽搐（决策每帧可能翻），必须改成「进入路口时锁存、离开时清空」的确定性规则（它其实有 `intersection_decision` 缓存，但只在 `-1` 时才摇一次，边界条件写得很脆）。
- **硬编码像素阈值（24.0 / 48.0）**：抄公式可以，抄常数不行，我们的格尺寸/单位半径不同。

## 3. Boids（Reynolds 1987）

- 论文（我读的全文镜像）：<https://www.cs.toronto.edu/~dt/siggraph97-course/cwr87/>
- 原始出处：Craig W. Reynolds, *Flocks, Herds, and Schools: A Distributed Behavioral Model*, Computer Graphics 21(4), July 1987, pp. 25–34（SIGGRAPH '87）
- 作者主页（本次 fetch 失败，仅作引用）：<https://www.red3d.com/cwr/boids/>

### 它到底做了什么（一句话）

把一群鸟拆成「每只鸟只看邻居」的独立 actor，用三条局部规则（避碰 / 速度匹配 / 聚集）产生整体群飞，并给出几何飞行与限速/限加速度的运动模型。

### 关键技术点（【读到】论文原文）

**三条规则，明确按优先级递减排列：**

1. **Collision Avoidance**（避碰，避让近邻）
2. **Velocity Matching**（速度匹配，对齐）
3. **Flock Centering**（聚集，向邻居中心靠）

论文原话：*"in order of decreasing precedence"*。**注意是优先级，不是加权求和**——这是和网上大多数 boids 实现（`w1*sep + w2*ali + w3*coh`）最大的差别。

**"nearby" 的定义**：由「偏移向量的距离与方向」共同决定（不是纯半径球）；论文引述真实鸟群可能只在意「自己 + 最近 2~3 个邻居 + 其余群体」，并据此论证真实鸟群是 O(1) 算法。

**运动模型（对我们的「连续运动 + 路权」直接有用）：**

- 有 **max speed** 与 **min speed**（`min speed` 默认 0）；
- 有 **max acceleration**，且**以 max speed 的比例表示**，用来「截断过于急躁的加速度请求」，从而得到平滑的转向与速度变化；
- 有粘性速度阻尼（viscous speed damping），所以持续加速不会无限快；
- 转向靠把推力指向目标方向；bank（滚转）由侧向加速度决定。

**复杂度与 remedy（论文自己说的）**：朴素实现 O(N²)；解法是「把 boids 分到空间 lattice 的 bin 里」+「增量碰撞检测」，以及「一鸟一处理器 → O(N)」。作者明确说：「**如果有个办法把 N 压得很小，O(N²) 也能接受**」。

### 有没有量化数字

- 有，而且是**很好的反面基准**：80 只 boid、朴素 O(N²)（6400 次两两比较）、在 Symbolics 3600 Lisp Machine（无加速硬件）上 **约 95 秒/帧**；一段 10 秒（300 帧）测试片渲了**约 8 小时**。【读到】
- 论文**没有给三条力的具体权重数值**（只有优先级 + 限幅）。任何 `1.0 / 0.8 / 0.5` 之类的权重都是后人实现约定，不是论文数据。【推断】

### 对我们的可借鉴点

**能直接落地：**

1. **优先级式混合，而不是加权和**。我们的「互斥力 + 路权 + 流场吸引」正需要这个结构：
   - 第 1 优先：硬约束（不重叠、不穿墙）→ 直接位置投影，不参与加权；
   - 第 2 优先：路权/让行 → 只改「期望速度」，不改位置；
   - 第 3 优先：流场方向 + 阵型 slot 吸引 → 加权求和。
   这比「所有力加起来再归一化」稳得多（加权和会让「避碰」被「聚集」抵消，正是 §5 评论区说的「一碰就弹开/疯狂抖动」的根因之一）。
2. **两段限幅**：先截断 **加速度**（max_force，按 max_speed 的比例给），再截断 **速度**（max_speed）。我们现在如果直接 `velocity += force`，然后 `normalize * max_speed`，等于把加速度信息丢掉、只留方向（§1 就是这么写的，结果单位永远全速跑）。RTS 需要「起步/刹停/被挤开」的加减速手感，必须保留加速度限幅。

**不适合，以及为什么：**

- **alignment / cohesion 不要照搬到 RTS**。这两条是为「无碰撞的流体感」服务的；RTS 的同类单位需要的是**保持间距的阵型**（slot + 硬最小距离），照搬会出现「一队坦克挤成一个球」。
- **论文的 3D 几何飞行（bank、lift、重力）对我们完全无关**，2D 网格 RTS 只需要 2D 转向 + 限幅。

## 4. RVO2 library（ORCA）

- 官网：<https://gamma.cs.unc.edu/RVO2/>
- 文档（参数语义）：<https://gamma.cs.unc.edu/RVO2/documentation/2.0/params.html>
- 源码：<https://github.com/snape/RVO2>（982★，Apache-2.0，v2.0.2 / 2016；当前 main 已重构成 `.cc` + bazel/meson）
- ORCA 论文页：<https://gamma.cs.unc.edu/ORCA/>

### 它到底做了什么（一句话）

每个 agent 只和邻居「各让一半」地构造半平面约束（ORCA lines），再用一个小型 2D 线性规划求出「最接近期望速度、又不撞」的新速度；`prefVelocity` 由调用方（我们的流场）给。

### 关键技术点（全部【读到】`src/Agent.cc`）

**每帧流程**

```
computeNeighbors(KdTree)
  ├─ 障碍：range = timeHorizonObst * maxSpeed + radius
  └─ 邻居：range² = neighborDist²，保留 maxNeighbors 个最近的（插入排序维护，满了就把 range² 收紧成当前最远者）
computeNewVelocity(timeStep)
  ├─ 先造「障碍 ORCA 线」（含 alreadyCovered 去重、凸/凹顶点、左右腿投影）
  ├─ 再造「agent-agent ORCA 线」（每对一条）
  ├─ linearProgram2(orcaLines, maxSpeed, prefVelocity, false) → 失败则
  └─ linearProgram3(...)  // 最小化「最大穿透」，保底可行
update(timeStep): position += velocity * timeStep
```

**agent-agent 半平面构造（最核心的 20 行，照这个抄）**

```cpp
if (distSq > combinedRadiusSq) {                    // 未重叠
  const Vector2 w = relativeVelocity - invTimeHorizon * relativePosition;
  const float wLengthSq = absSq(w), dotProduct = w * relativePosition;
  if (dotProduct < 0 && dotProduct*dotProduct > combinedRadiusSq * wLengthSq) {
    // 投影到「截断圆」上
    const Vector2 unitW = w / sqrt(wLengthSq);
    line.direction = Vector2(unitW.y(), -unitW.x());
    u = (combinedRadius * invTimeHorizon - wLength) * unitW;
  } else {                                          // 投影到「腿」上
    const float leg = sqrt(distSq - combinedRadiusSq);
    if (det(relativePosition, w) > 0)               // 左腿
      line.direction = Vector2(rp.x*leg - rp.y*cr, rp.x*cr + rp.y*leg) / distSq;
    else                                            // 右腿
      line.direction = -Vector2(rp.x*leg + rp.y*cr, -rp.x*cr + rp.y*leg) / distSq;
    u = (relativeVelocity * line.direction) * line.direction - relativeVelocity;
  }
} else {                                            // 已重叠：改用 timeStep 而不是 timeHorizon
  const Vector2 w = relativeVelocity - invTimeStep * relativePosition;
  const Vector2 unitW = w / abs(w);
  line.direction = Vector2(unitW.y(), -unitW.x());
  u = (combinedRadius * invTimeStep - wLength) * unitW;
}
line.point = velocity_ + 0.5F * u;                  // ★ 责任分摊 50/50
orcaLines_.push_back(line);
```

三个要点：

- **`u` = 「相对速度至少要挪多少才脱离速度障碍」**，方向取垂直于 `unitW` 的那条切线。
- **`line.point = v + 0.5u`**：把自己该让的那一半直接折进半平面的偏移里 —— 这就是「互惠」的全部魔法，双方各让一半，不会互相弹。
- **重叠时把 `timeHorizon` 换成 `timeStep`**：已重叠就不能再等 2 秒，必须「这一帧就分开」，这是防抖/防穿插的关键分支（很多人抄 ORCA 抄漏这段，才会「一碰就弹开」）。

**LP 求解（3 变量：vx, vy, dist）**

- `linearProgram1(lines, lineNo, radius, optVelocity, directionOpt)`：在**某条直线**上求满足圆约束 `|v| ≤ radius` 的可行区间，用判别式 `dot² + r² - |point|²` 判空，再和前面每条线求交收紧 `tLeft/tRight`（平行用 `RVO_EPSILON` 特判）；`directionOpt` 决定「沿方向取极值」还是「取离期望速度最近的点」。
- `linearProgram2`：先取「期望速度按 radius 截断」的初值，逐条约束检查 `det(dir, point - result) > 0`，违反就在那条线上重解；一旦某条线无解，返回失败的行号。
- `linearProgram3`：把失败行之前的所有「非障碍」约束两两求交投影成新线（`projLines`），以「最小化最大穿透」为目标重解（`directionOpt = true`），并维护 `distance` 单调推进。注释里明说：理论上不该失败，失败只可能是浮点误差，此时保留旧结果。
- **LP 变量只有 3 个、约束数是邻居数**，所以「每 agent 一遍 LP」是 O(k) 的，k = maxNeighbors。

**参数（文档只给语义，不给默认值）**

`timeStep`；每 agent：`maxNeighbors`、`maxSpeed`、`neighborDist`、`radius`、`timeHorizon`、`timeHorizonObst`、`prefVelocity`、`velocity`、`position`。
语义要点【读到文档】：`timeHorizon` 越大 → 越早开始避让、但速度自由度越小；`maxNeighbors` / `neighborDist` 太小 → 不安全，太大 → 慢。

### 有没有量化数字

- **官网没有任何 benchmark 数字**。唯一的「性能背书」是一条媒体评价：Warhammer 40,000: Space Marine 用了该技术，"no matter how many orks are barreling your way ... the framerate never takes a hit"（Telegraph, 2011）【读到官网引用】。
- 并行方式是 OpenMP（按 agent 并行）。【读到官网】

### 对我们的可借鉴点

**能直接落地（这是短程避让最值得抄的一份）：**

1. **`line.point = v + 0.5u` 的责任分摊**。我们的 RTS 不一定需要完整 LP：**只做「每条半平面做一次投影（clamp 到半平面内侧）」再平均**，就能拿到 80% 的效果，成本是 O(k) 无排序、无迭代。完整 LP 只在「约束互相冲突（窄口/门口）」时才需要，可用 §4 的 LP3 作为兜底。
2. **`timeHorizon` 概念**：把「多近才需要避让」变成「速度 × 时间」的判据，而不是固定半径。RTS 里正好用来表达**路权**：让行方用大 `timeHorizon`（早让、让得多），抢行方用小 `timeHorizon`（晚让）；再把 `0.5u` 换成不对称的 `αu / (1-α)u`，就是「责任分配比例」。这是我认为**把 ORCA 改造成「路权」系统最自然的一步**。【推断，但基于原文的责任分摊结构】
3. **「已重叠 → 用 timeStep 而不是 timeHorizon」分支**。这正是我们现在「离散格占位 → 连续运动」最容易踩的坑：单位叠在一起时用 2 秒的规划视野去分离，会得到巨大且方向互斥的修正量 → 抖动。抄这个分支即可。
4. **LP3 的「最小化最大穿透」退化策略**：死锁/窄口的最后一道保险，比「随便取一个可行速度」稳。

**不适合，以及为什么：**

- **完整 ORCA + KdTree + 每 agent 一次 LP 的规模上限**。RVO2 的目标是「几百到几千个同质 agent 的平滑人流」，且**假设所有 agent 都愿意合作、速度量级相近**。RTS 里单位有「停下开火 / 攻击时不动 / 阵型 slot / 建筑占格」，这些用 `prefVelocity=0` 硬塞进 ORCA 会得到「被推着走」的怪异行为（§5 的评论区里就有人抱怨「攻击时冻结移动」「被挤开要专门写逃逸」）。【推断，基于 ORCA 的假设与 RTS 需求差异】
- **每帧 KdTree 重建**：bevy 里我们已经有网格，直接用格 bucket 取邻居更便宜；不要为了 ORCA 引入 kd-tree。
- **`maxNeighbors` 全用上**：RTS 高密度推进时，一格 5–15 个邻居 × 每对一条半平面，成本会爆。建议**硬上限 4–8 个**，按「距离 + 是否同方向」筛。

### 5A. GitHub：KisaragiTomi/GPU-Crowd-Godot（项目名 FluidCrowd）

- 仓库：<https://github.com/KisaragiTomi/GPU-Crowd-Godot>
- 栈：Godot 4.6（自编译，Vulkan 后端）+ GDScript + GLSL 450 compute；21★；2026-03-28 建仓，2026-10-10 最后 push【读到】

#### 它到底做了什么（一句话）

把「密度当水位」的**浅水方程（SWE）压力场** + **每帧轮转的多阵营 BFS 目标场** + **GPU 空间哈希 + 硬最小距离投影** 拼成一个全 GPU 的 10 万人同屏 2D 群集/战斗模拟。

#### 关键技术点（全部【读到】ReadME + shader）

| 项 | 值 |
|---|---|
| Agent 上限 | **100,000** |
| 阵营 / 目标组 | **32 / 32** |
| 网格 | **800 × 480**，`cell_size = 8 px` |
| 数据布局 | **SoA**（pos_x / pos_y / vel_x / vel_y 分离）+ **ping-pong 双缓冲** |
| 空间哈希 | 4 pass：`clear → count(原子加) → prefix_sum(单个 1024 线程工作组，按 4096 格分块做 exclusive scan，经 shared memory) → scatter` |
| 邻居半径 | `R = 3` 格（3×3 cell 扫描） |
| 寻路 | BFS 目标场，**每帧只更新 1 个目标组（32 组轮转）** |

**每帧管线（单次 `compute_list` + barrier 串联）**：空间哈希 → 密度 splat（双线性）+ 阵营 presence（**32-bit 位掩码**）→ SWE flux（**节流约 33 ms 一次**）→ 速度场（flux 差分 + 目标梯度 + 密度自适应减速 + 地面难度）→ 战斗（距离场门控 + 3×3 presence 扫描）→ 阻挡掩码 → **Steer + 积分** → MultiMesh 缓冲构建 → 激光压缩（≤8192 条）→ 选中查询（只回读 64 字节）→ Goal BFS（1 组）。

**压力场（SWE）怎么做**：把 **agent 密度当作水面高度 H**，叠加目标距离场与地形墙作为势能，四方向 flux 传播 → 自然形成「从高密度流向低密度」；`swe_flux.glsl` 用 **8×8 工作组 + halo** 读共享内存；`swe_velocity.glsl` 用「flux 差分 + 目标梯度混合」，再按密度与地面难度减速。

**BFS 目标场（这块最值得抄）**：

1. **Init**：有敌方 presence 的格 = 0；墙 = `0xFFFFFFFF`；其余未到达。
2. **分块松弛**：每组把 **16×16 tile + 1 格 halo** 读进 shared memory，**在 tile 内迭代到不再变化再写回**；每帧预算 **80 次全局 pass**；全图无变化后整组提前退出。
3. **双距离**：`goal_dist_all` 保留**未加权格数距离**给战斗射程用；`goal_dist`（+ 归一化梯度）来自**加权移动代价**给导航用。→ 单位会绕开泥地，但远程射程不会因为泥地变短。
4. 开局（启动/重置）先在 GPU 上从地图中心批量迭代收敛一次，写入全部 32 组作为初值。梯度方向优先查预算好的 `_ensure_dir_lut` 表。

**Steer 段（`agent_steer.glsl`，对「互斥力 + 压力场 + 路权」最直接）**：

```glsl
// 1) 双线性采样速度场（目标速度）
// 2) 3×3 格邻居分离力：
float f  = 1.0 - dd * inv_sep_r;          // 软截断，d≥sep_r 时为负→不施力
float ff = sep_strength * f * f / dd;     // ★ f² / d，兼具「近处平方增强」和「除以距离」
vsx += djx * ff;  vsy += djy * ff;
// 3) 攻击者加成（路权/穿透感的原型）：
//    对方在攻击、我不在攻击 → ff *= 8.0（敌方）/ *= 0.1（友方）
//    atk_impede = max(atk_impede, f)   // 记录被挡住的程度
// 4) 墙壁排斥：四邻查 terrain，wpx/wpy 各 ±1，wall_repel = 40.0
// 5) 高密度噪声破对称：if (n_count > 6) amp = (n_count - 6) * 3.0，加到分离力上
// 6) 卡死检测 → 切向逃逸（stall → tangential escape）
// 7) 硬最小距离投影：min_dist = cell_size * 0.75，按距离分档 push_frac = 0.5 / 1.0
// 8) 地形碰撞轴分离 + 卡墙自动推出
```

**战斗/占格**：距离场门控（目标场距离 > 射程 + 2 格 且 3×3 无敌方 presence 就跳过索敌）→ 远程不会隔墙打；**攻击时冻结移动**；同一格被多个攻击者占用时，其余单位被 `displaced`，在 steer 里**就地扫 7×7 邻域找最近空格逃逸**。

#### 有没有量化数字

有，但**是局部 pass 的 ms，不是整帧 FPS**【读到 `MEMORY.md`】：

### 对我们的可借鉴点

**能直接落地（我认为这是 6 个里最该照抄的）：**

1. **压力场就用「密度 → 高度场 → flux 扩散 → 速度」这条链**。我们不需要真的解 SWE，只要：
   - 每 tick 把单位位置双线性 splat 到格子上得到 `density`；
   - 对 `density` 做 N 次（1–3 次足够）四邻域扩散/松弛，得到 `pressure`；
   - 单位速度 += `-∇pressure * k`（或直接取「低压力方向的切向」）。
   这比「一堆弹簧互斥」稳，因为**压力是全局平滑量，不会被两个单位的瞬时重叠放大成抖动** —— 正好解决视频评论区那个「弹簧抖」问题。
2. **多目标场轮转 + 每帧预算**：32 个阵营目标场，每帧只更新 1 组，30 帧一轮。RTS 里我们只需要 2–8 个玩家/编队目标场，完全可以「1–2 个/帧 + 预算上限 + 无变化提前退出」，把 BFS 摊平到多帧，**长程流场永远不会成为尖峰**。
3. **双距离（加权代价给导航 / 未加权给射程）**：RTS 里这个分离极其有用 —— 寻路绕开泥地/减速地形，但**射程按格数算**，不会出现「站在泥地里射程变短」的荒谬。
4. **硬最小距离投影 `min_dist = cell * 0.75` + 分档 `push_frac`**：这是「连续运动」不穿模的最后一道保险，且比纯力稳定（力负责手感，投影负责正确性）。0.75 格这个比例可以直接拿来当起点。
5. **卡死检测 → 切向逃逸（stall → tangential escape）+ 7×7 找最近空格**：这就是我们「路权/让行」要的兜底 —— 让不动的时候，沿切线走一格，而不是原地推。
6. **32-bit 阵营 presence 位掩码**：一张 `u32` 图搞定「这格有哪些阵营」，索敌/阻挡/占格判定全能 O(1)。
7. **`f²/d` 的分离力写法**：`f = 1 - d/r`，`ff = strength * f² / d`。比 §1 的 `1/d` 好，因为 `f` 在 `d → r` 时自然归零（C¹ 连续，无阈值跳变），且 `f²` 让近处增强得更快。

**不适合，以及为什么：**

- **全 GPU 管线本身**。我们是 CPU 侧 bevy ECS + 网格 RTS，单位数目标大概率 500–2000，不是 10 万；把逻辑搬 GPU 会换来「单位逻辑不能复杂、不好扩展」（作者自己承认）以及「回传延迟」，而 RTS 需要频繁的**确定性查询**（选中、攻击判定、路径事件、存档/重放）。**抄结构，不抄执行位置。**
- **SWE 真解（flux + 33 ms 节流）**：33 ms 才更新一次压力场，对 RTS 的「瞬间挤开」太慢；我们只需要「扩散几次」的近似，不需要守恒律。
- **攻击时冻结移动**：这是他们为了省事/好判定做的取舍，RTS 里会让单位看起来「卡住」，我们可以改成「减速 + 原地转向」。
- **每帧 80 pass 的 BFS 预算**：在 CPU 上不可行；我们用「格数上限 + 分帧」而不是「pass 数上限」。

### 这类实现的标准做法（【推断】/ 通用知识，不是某个仓库的结论）

GPU 并行 BFS 做流场，工业界常见骨架是：

1. **双缓冲距离场**：`dist_in` / `dist_out`，每个 pass 只读旧、写新。
2. **水平同步推进**：每 pass 对每格检查四/八邻，`dist_out[i] = min(dist_in[nb]) + cost[i]`；一轮只推进「一层」，所以最坏 pass 数 = 图的直径。
3. **原子/前缀和做 frontier**：活跃格压缩成紧凑列表（count → prefix sum → scatter），只对 frontier 派发，避免全图空转。§5 的 4-pass 空间哈希就是这个套路的实例。
4. **收敛判据**：全局 `changed` 标志 + 提前退出；或者用「tile 内迭代到不动再写回」的分块松弛（§5 的做法，能大幅减少全局 pass）。
5. **加权代价时的坑**：BFS 只能处理均匀代价；带地形代价要用 **Dijkstra / 桶排序（bucket queue）** 或多次松弛（会退化成 Bellman-Ford 的 pass 数）。§5 就是「加权 + 未加权双距离」硬算，代价是 pass 预算。

对我们的直接结论：**CPU 侧不需要 GPU 并行 BFS**。RTS 一张图 128×128～256×256 格，单线程 BFS 也就零点几毫秒；真正要分帧的是「多目标场 × 多阵营」。用「每帧更新 1–2 个目标场 + 脏格增量」即可，别上并行/GPU。

## 8. 结论（10 行以内）

1. **最该照抄的第一名：GPU-Crowd-Godot（§5A）**——抄它的「结构」，不抄它的 GPU 执行位置。
2. 具体抄四块：**密度→扩散→压力场**（替代弹簧式互斥，天然抗抖）、**硬最小距离投影 `0.75×cell`**（正确性兜底）、**卡死→切向逃逸 + 最近空格**（路权的兜底）、**多目标场每帧轮转 + 预算**（长程流场永不尖峰）。
3. **第二名：RVO2（§4）**——但只抄三行：`line.point = v + 0.5u` 的**责任分摊**、**已重叠改用 timeStep** 的分支、**LP3 最小化最大穿透**的退化策略。
4. 把「0.5」改成不对称的 `α`，就是**路权**：让行方 `α` 大 + `timeHorizon` 大，抢行方反之。这是把 ORCA 变成 RTS 规则最省力的一步。
5. **第三名：Boids 的「优先级混合 + 加速度/速度两段限幅」**——只要这两条，不要 alignment/cohesion（RTS 会挤成球）。
6. **反面教材：compute_battle_sim 的排序管线**——52 万单位时 190 次 dispatch + 每次新建 uniform buffer，这是「帧率越跑越低」的典型来源；我们 CPU 侧用计数排序/格 bucket。
7. **bevy_crowd_sim 只抄一个技巧**：`fract(sin(...))` 确定性随机，用于打破抢行对称。
8. **gpu_pathing 查无此源**，别在它身上花时间；要性能基准就看 §6 的 epheria 数据（流场 <10% 帧时间，排序 37%）。
9. 落地顺序建议：**先压力场 + 硬投影**（把抖动和穿模压住）→ **再加 ORCA 式责任分摊做路权** → **最后才谈阵型/攻击冻结**。
10. 一句提醒：这 5 个 GPU 项目的 FPS 数字**全部不可移植**到 CPU 侧网格 RTS；可移植的只有公式、参数比例、和「力负责手感、投影负责正确性」的分工。
